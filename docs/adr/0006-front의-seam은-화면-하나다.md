# front의 seam은 화면 하나다

스캐폴딩 스펙은 `front-react`에 자동 테스트를 두지 않기로 하면서 "컴포넌트 테스트 도구 도입은 그 자체로 별도 결정"이라고 미뤄뒀고, 같은 문서가 그곳을 **"seam이 비는 유일한 지점"**이라고 적었다. 이제 도입한다. 도구는 Vitest + Testing Library이고, 네트워크는 MSW가 가로챈다.

무엇을 seam으로 삼을지가 진짜 결정이다. back이 컨트롤러·서비스·리포지토리를 따로 검사하지 않고 **HTTP 하나**만 두었듯, front도 **사용자가 보는 화면 하나**만 둔다. 훅이나 컴포넌트를 떼어내 검사하지 않고, 라우터·인증·서버 상태를 다 끼운 앱을 세운 뒤 실제로 타이핑하고 클릭한다. 가짜를 두는 자리는 딱 한 곳, 네트워크 경계다.

## Considered Options

- **Playwright로 진짜 스택을 띄우고 검사.** 가장 사실에 가깝지만 back과 DB를 함께 띄워야 하고 느리다. back의 HTTP seam 테스트가 이미 서버 쪽 진실을 지키고 있어서, front에서 다시 확인할 값이 크지 않다.
- **컴포넌트 단위 테스트.** 버튼 하나, 훅 하나를 따로 검사하는 방식. 리팩터링할 때마다 같이 깨지고, 정작 "글이 화면에 보이는가"는 답하지 못한다.

## Consequences

- 테스트는 back 없이 돈다. `npm test` 하나로 끝난다.
- MSW 핸들러가 back의 계약(상태 코드와 ProblemDetail 모양)을 흉내 낸다. **그 계약이 실제로 지켜지는지는 back의 HTTP seam 테스트가 본다.** 계약이 바뀌면 양쪽을 함께 고쳐야 하고, 안 고치면 front 테스트는 통과하는데 실제로는 깨지는 구간이 생긴다. 이 방식의 가장 큰 약점이다.
- 화면을 접근성 이름으로 찾는다(`getByLabelText('본문')`). 라벨이 없으면 테스트가 실패하므로, 스크린리더가 읽을 수 있는지가 자동으로 검사된다 — 실제로 이 테스트를 처음 돌릴 때 본문 입력칸에 `label`이 없던 것이 잡혔다.
- 새니타이징을 상세와 작성 미리보기 양쪽에서 검사한다. 마크다운 렌더러를 손대면 두 곳이 함께 걸린다.
- `jsdom`에는 `matchMedia`가 없어 테마 코드가 죽는다. 셋업에서 채운다.
- `.env.test`가 필요하다. `env.ts`가 API 주소 없이는 일부러 죽기 때문이다.
