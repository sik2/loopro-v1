# Loopro 스캐폴딩

Status: done

## Problem Statement

Loopro는 블로그 기능을 기반으로 교안을 작성·공유하는 플랫폼이 될 예정이지만, 지금 저장소에는 실행되는 것이 하나도 없다. `CONTEXT.md`와 ADR 두 건, 에이전트 규약 문서만 있고 코드는 0줄이다.

글을 쓰려는 사람은 가입할 곳도, 글을 저장할 곳도, 남의 글을 읽을 곳도 없다. 무엇을 만들지 논의하려 해도 눈으로 확인할 대상이 없어서 모든 판단이 추상적으로 남는다.

## Solution

`back`(Spring Boot REST API)과 `front-react`(React 웹)로 이루어진, 로컬에서 실행되는 최소 플랫폼을 세운다. 회원이 가입·로그인하고, `Post`를 마크다운으로 쓰고 발행하고, 서로의 글에 `Comment`를 달고 추천할 수 있다.

이번 결과물은 **교안 플랫폼이 아니라 블로그다.** 교안을 일반 글과 구별하는 요소(시리즈 목차, 강 단위 구조, 코드블록 raw 공유)는 이번 범위에서 제외했다. ADR-0001에 따라 교안은 별도 엔티티가 아니라 긴 `Post`이므로, 그 요소들은 나중에 `Post` 위에 기능으로 얹힌다.

## User Stories

### 계정

1. 방문자로서, `Username`·비밀번호·`Nickname`으로 가입하고 싶다. 그래야 글을 쓸 수 있다.
2. 방문자로서, 이미 쓰이는 `Username`으로 가입하려 하면 거부당하고 싶다. 그래야 로그인 식별자가 유일하게 유지된다.
3. 방문자로서, 이미 쓰이는 `Nickname`으로 가입하려 하면 거부당하고 싶다. 그래야 화면에서 사람을 구분할 수 있다.
4. 방문자로서, 가입 입력값이 형식에 맞지 않으면 어느 항목이 왜 틀렸는지 항목별로 알고 싶다. 그래야 무엇을 고쳐야 할지 안다.
5. 방문자로서, `Username`과 비밀번호로 로그인해 토큰을 받고 싶다. 그래야 인증이 필요한 기능을 쓸 수 있다.
6. 방문자로서, 틀린 비밀번호로 로그인하면 거부당하고 싶다. 그때 `Username`이 존재하는지 여부는 알려주지 않아야 한다.
7. `Member`로서, 내 `Nickname`과 `Role`을 포함한 내 정보를 조회하고 싶다. 그래야 어떤 계정으로 로그인했는지 확인할 수 있다.
8. `Member`로서, 로그아웃하면 브라우저에 저장된 토큰이 지워지길 원한다. 그래야 같은 브라우저를 쓰는 다른 사람이 내 계정을 쓰지 못한다.
9. `Member`로서, 만료된 토큰으로 요청하면 인증 실패로 거부당하고 싶다. 그래야 오래된 세션이 무한정 살아있지 않다.
10. 방문자로서, 토큰 없이 인증이 필요한 기능을 호출하면 401로 거부당하고 싶다.
11. `Member`로서, 권한이 없는 대상을 조작하려 하면 403으로 거부당하고 싶다. 그래야 401(누구인지 모름)과 구분된다.

### Post 읽기

12. 방문자로서, 로그인하지 않고도 발행된 `Post` 목록을 보고 싶다. 그래야 가입 전에 이 플랫폼에 뭐가 있는지 판단할 수 있다.
13. 방문자로서, `Post` 목록을 페이지 단위로 넘기고 싶다. 그래야 글이 쌓여도 한 번에 다 받지 않는다.
14. 방문자로서, 목록에서 각 `Post`의 제목·작성자 `Nickname`·작성일·`ViewCount`·추천수·댓글수를 보고 싶다. 그래야 무엇을 읽을지 고를 수 있다.
15. 방문자로서, `Post` 상세를 열어 본문을 읽고 싶다.
16. 방문자로서, 마크다운으로 쓰인 본문이 제목·목록·표·코드블록으로 렌더링돼 보이길 원한다. 그래야 교안을 읽을 수 있다.
17. 방문자로서, `Post` 상세를 열 때마다 `ViewCount`가 올라가길 원한다. 그래야 작성자가 반응을 가늠할 수 있다.
18. 방문자로서, 존재하지 않는 `Post`를 열면 404로 명확히 안내받고 싶다.

### Post 쓰기

19. `Member`로서, 제목과 마크다운 본문으로 `Post`를 작성하고 싶다.
20. `Member`로서, `Post`를 발행하지 않은 상태로 저장하고 싶다. 그래야 완성 전에는 남에게 보이지 않는다.
21. `Member`로서, 발행하지 않은 내 `Post`를 나만 볼 수 있길 원한다. 목록에도 남에게는 뜨지 않아야 한다.
22. `Member`로서, 나중에 `Published` 상태로 바꿔 발행하고 싶다.
23. `Member`로서, 발행한 `Post`를 다시 비발행으로 되돌리고 싶다. 그래야 잘못 올린 글을 내릴 수 있다.
24. `Member`로서, 내 `Post`의 제목과 본문을 수정하고 싶다.
25. `Member`로서, 남의 `Post`를 수정하려 하면 거부당하고 싶다.
26. `Member`로서, 내 `Post`를 삭제하고 싶다.
27. `Member`로서, 남의 `Post`를 삭제하려 하면 거부당하고 싶다.
28. `ADMIN`으로서, 아무 `Post`나 삭제할 수 있길 원한다. 그래야 문제되는 글을 정리할 수 있다.
29. `ADMIN`으로서, 남의 `Post`를 수정하는 것은 불가능하길 원한다. 삭제는 관리 행위지만 수정은 위조이기 때문이다.
30. `Member`로서, `Post`가 삭제되면 딸린 `Comment`와 추천 기록도 함께 사라지길 원한다. 그래야 고아 데이터가 남지 않는다.

### Comment

31. 방문자로서, `Post` 상세에서 달린 `Comment`를 전부 보고 싶다.
32. `Member`로서, `Post`에 `Comment`를 달고 싶다.
33. `Member`로서, 내 `Comment`를 수정하고 싶다.
34. `Member`로서, 내 `Comment`를 삭제하고 싶다.
35. `Member`로서, 남의 `Comment`를 수정하거나 삭제하려 하면 거부당하고 싶다.
36. `ADMIN`으로서, 아무 `Comment`나 삭제할 수 있길 원한다.
37. 방문자로서, 각 `Comment`의 작성자 `Nickname`과 작성일을 보고 싶다.
38. `Member`로서, 발행되지 않은 `Post`에는 (작성자 본인이 아닌 한) `Comment`를 달 수 없길 원한다.

### 추천

39. `Member`로서, `Post`를 추천하고 싶다. 그래야 좋은 글을 표시할 수 있다.
40. `Member`로서, 이미 추천한 `Post`를 다시 추천하려 하면 중복으로 쌓이지 않길 원한다.
41. `Member`로서, 추천을 취소하고 싶다.
42. `Member`로서, 내가 이 `Post`를 이미 추천했는지 화면에서 알고 싶다. 그래야 버튼 상태가 실제와 맞는다.
43. 방문자로서, `Post`의 추천수를 보고 싶다.
44. `Member`로서, `Comment`에도 똑같이 추천하고 취소할 수 있길 원한다.
45. 방문자로서, `Comment`의 추천수를 보고 싶다.
46. 방문자로서, 로그인하지 않고 추천하려 하면 로그인하라고 안내받고 싶다.

### 개발자

47. 개발자로서, 앱을 처음 띄우면 회원 5명·글 5개·댓글 5개가 이미 들어 있길 원한다. 그래야 빈 화면부터 시작하지 않는다.
48. 개발자로서, 이미 회원이 있으면 샘플 데이터 생성이 건너뛰어지길 원한다. 그래야 재시작할 때마다 데이터가 불어나지 않는다.
49. 개발자로서, 샘플 회원 중 하나가 `ADMIN`이길 원한다. 그래야 권한 분기를 바로 확인할 수 있다.
50. 개발자로서, 개발 모드에서 앱을 껐다 켜도 데이터가 남아 있길 원한다.
51. 개발자로서, 테스트는 매번 빈 DB에서 시작하길 원한다. 그래야 테스트끼리 간섭하지 않는다.
52. 개발자로서, 브라우저에서 h2-console로 개발 DB를 들여다보고 싶다.
53. 개발자로서, Swagger UI로 API 계약을 확인하고 싶다. 그래야 front 작업이 back 코드를 읽지 않아도 된다.
54. 개발자로서, 설정이 깨지면 앱을 띄우기 전에 테스트가 알려주길 원한다.
55. 개발자로서, front 개발 서버에서 back API를 호출할 때 CORS로 막히지 않길 원한다.

## Implementation Decisions

### 전체 구조

- `back`은 REST API만 낸다. 서버 렌더링 화면은 없다. 화면은 전부 `front-react`가 그린다.
- `infra`와 `front-kmp`는 이번에 건드리지 않는다. `README`만 둔다.
- 배포하지 않는다. 로컬 실행만 다룬다.

### back

- Spring Boot 4.1.1, JDK 25, Gradle Kotlin DSL. 언어는 Java.
- 루트 패키지 `com.back`, 메인 클래스 `BackApplication`에 JPA auditing 활성화.
- 패키지는 `domain`과 `global`로 나눈다. `domain` 아래에 계정 묶음과 글 묶음을 두고, 글 묶음 안에 `Post`·`Comment`·`PostLike`·`CommentLike`를 함께 둔다. 이 넷은 한 덩어리로 움직인다.
- 모든 엔티티는 공통 상위 클래스를 상속한다. 이 클래스가 식별자와 작성일·수정일을 함께 갖고, 작성일·수정일은 JPA auditing이 채운다. `equals`/`hashCode`는 식별자 기준으로 구현한다 — Hibernate의 lazy proxy는 실제 클래스가 다르므로 클래스 비교를 쓰면 안 된다.
- OSIV를 끈다. 트랜잭션은 서비스의 액션 메서드 레벨에 건다. 컨트롤러는 엔티티가 아니라 DTO를 받는다.
- 의존성: Spring Web, Spring Data JPA, Validation, Spring Security, Lombok, DevTools, H2, springdoc-openapi.

### 설정 프로파일

- 공통 설정은 기본 설정 파일에 두고, 개발·테스트 프로파일 파일이 각각 덮어쓴다.
- 개발 프로파일: H2 파일 DB(`back` 디렉터리 기준 `db_dev.mv.db`), 스키마 자동 갱신, h2-console 활성화.
- 테스트 프로파일: H2 인메모리 DB, 스키마 매번 생성, h2-console 없음.
- DB 파일은 버전 관리에서 제외한다.

### 인증

- ADR-0002에 따라 JWT access token을 쓴다. refresh token은 없다.
- 토큰 유효기간은 7일. 서명 키는 개발 프로파일에 기본값을 두되 환경변수로 덮어쓸 수 있게 한다.
- 로그아웃은 클라이언트가 저장된 토큰을 버리는 것이 전부다. 서버는 토큰을 무효화하지 않는다.
- 비밀번호는 해시해서 저장한다. 평문 저장이나 가역 암호화는 쓰지 않는다.
- 인증 필터가 요청 헤더의 토큰을 읽어 보안 컨텍스트를 채운다.
- CSRF 보호는 끈다. 세션은 stateless로 둔다.
- 읽기 요청(글 목록·상세·댓글 목록)과 가입·로그인은 인증 없이 허용한다. 나머지 쓰기 요청은 인증을 요구한다.
- h2-console과 Swagger UI는 개발 프로파일에서만 열고, frame 관련 제약을 예외 처리한다.
- CORS 허용 출처는 설정 프로퍼티로 주입한다. 코드에 하드코딩하지 않는다.

### API 계약

- 성공 응답은 래퍼 없는 순수 DTO다. 클라이언트는 HTTP 상태 코드로 성공/실패를 판별한다.
- 모든 에러 응답은 RFC 9457 `ProblemDetail`이다. 서비스 계층은 상태 코드를 담은 전용 예외를 던지고, 전역 핸들러가 이를 변환한다.
- 입력값 검증 실패는 항목명과 메시지의 쌍을 담은 형태로 변환한다. front의 폼 검증과 1:1로 맞물리게 하기 위함이다.
- 목록은 오프셋 페이징을 쓴다. Spring의 페이지 객체를 그대로 직렬화하지 않고 얇은 DTO로 감싸며, 페이지 번호는 1부터 시작한다.
- `Comment` 목록은 페이징하지 않고 전부 내린다. 대댓글이 없고 스캐폴딩 단계이기 때문이다.
- `Post` 응답에는 추천수·댓글수·`ViewCount`가 함께 담긴다. 요청자가 인증된 경우 "내가 추천했는지" 여부도 담는다.

### 도메인 규칙

- `Post` 본문은 마크다운 텍스트로 저장한다. back은 마크다운을 해석하지 않는다. 렌더링은 front의 책임이다.
- `Published`가 아닌 `Post`는 목록과 상세 모두에서 작성자 본인에게만 보인다. 서비스 계층에서 거른다.
- `ViewCount`는 상세 조회 요청마다 무조건 1 증가한다. 같은 사람의 반복 조회를 구분하지 않는다. 따라서 상세 조회는 쓰기 트랜잭션이다.
- 추천은 카운터 컬럼이 아니라 기록 엔티티다. `Post`용과 `Comment`용을 별도 엔티티로 나눈다. 대상과 `Member`의 조합에 유일 제약을 건다.
- 수정은 작성자 본인만 가능하다. `ADMIN`도 남의 글·댓글을 수정할 수 없다.
- 삭제는 작성자 본인과 `ADMIN`이 가능하다.
- `Post` 삭제 시 딸린 `Comment`와 두 종류의 추천 기록이 함께 물리 삭제된다. 소프트 삭제는 쓰지 않는다.
- `Username`과 `Nickname`에 각각 유일 제약을 건다.
- `Member`에 이메일 필드는 없다.

### 초기 데이터

- 애플리케이션 시작 시 실행되는 러너가 샘플 데이터를 만든다. 트랜잭션 안에서 동작한다.
- `Member`가 한 명이라도 있으면 아무것도 하지 않고 종료한다.
- 회원 5명, `Post` 5개, `Comment` 5개를 만든다. 회원 중 한 명은 `ADMIN`이다.
- 샘플 `Post` 중 최소 하나는 발행되지 않은 상태로 둔다. 공개 범위 동작을 눈으로 확인하기 위함이다.
- 샘플 본문에는 마크다운 제목·목록·코드블록이 들어간다. 렌더링을 확인하기 위함이다.

### front-react

- Vite + React + TypeScript. Next.js는 쓰지 않는다.
- 라우팅은 클라이언트 사이드. 화면은 글 목록, 글 상세, 글 작성, 글 수정, 로그인, 회원가입, 내 정보. 글 경로는 `/p/:id` 형태를 따른다.
- `Comment`와 추천은 별도 화면 없이 글 상세 안에서 다룬다. `ViewCount`는 표시만 한다.
- 서버 상태는 데이터 페칭 라이브러리로 관리한다. 폼은 폼 라이브러리와 스키마 검증 라이브러리를 함께 쓰고, 스키마는 back의 검증 규칙과 맞춘다.
- 스타일은 Tailwind 4를 **Vite 플러그인으로** 통합한다. play CDN은 쓰지 않는다 — 브라우저에서 런타임에 CSS를 만드는 개발용 도구이기 때문이다.
- UI 컴포넌트는 shadcn 방식(헤드리스 프리미티브 + 유틸리티 조합)을 쓴다. DaisyUI는 쓰지 않는다.
- 본문 폰트는 Pretendard 다이나믹 서브셋을 CDN에서 불러온다.
- 마크다운 렌더러를 붙인다. 사용자 입력을 HTML로 그리므로 새니타이징이 필수다.
- 토큰은 브라우저에 저장하고 요청 헤더에 실어 보낸다. 401 응답을 받으면 저장된 토큰을 버리고 로그인 화면으로 보낸다.
- API 기본 주소는 환경변수로 주입한다.

## Testing Decisions

### 좋은 테스트의 기준

외부에서 관찰 가능한 동작만 검증한다. 서비스 메서드가 호출됐는지, 리포지토리가 어떤 쿼리를 날렸는지는 보지 않는다. 검증 대상은 HTTP 상태 코드, 응답 JSON의 값, 에러 응답의 형태, 그리고 **후속 요청으로 확인되는 상태 변화**다.

예를 들어 "추천 취소"는 취소 API가 200을 반환하는 것만으로 통과시키지 않는다. 취소 후 글을 다시 조회해 추천수가 줄었고 "내가 추천함"이 거짓인지 확인한다.

### seam

**seam은 하나다: HTTP API.** 전체 애플리케이션 컨텍스트를 띄우고 테스트 프로파일(인메모리 DB, 매번 스키마 생성) 위에서 MockMvc로 요청을 보낸다. 서비스·리포지토리 단위 테스트는 두지 않는다.

이 한 지점에서 `ViewCount` 증가, 추천 토글과 중복 방지, 권한 거부, 비공개 `Post`의 가시성, 연쇄 삭제까지 전부 검증된다. seam을 늘릴 이유가 없다.

인증이 필요한 요청을 위해 로그인 후 토큰을 얻어 헤더에 싣는 공통 지원 코드를 둔다. 각 테스트가 인증 절차를 반복하지 않게 한다.

### 테스트 대상

- 계정: 가입 성공, `Username` 중복 거부, `Nickname` 중복 거부, 검증 실패 응답 형태, 로그인 성공, 잘못된 비밀번호 거부, 내 정보 조회, 토큰 없는 요청 거부.
- `Post`: 목록 페이징, 상세 조회, `ViewCount` 증가, 작성, 수정, 남의 글 수정 거부, 삭제, 남의 글 삭제 거부, `ADMIN`의 삭제 허용, 비공개 글이 목록·상세에서 안 보임, 작성자 본인에게는 보임, 삭제 시 `Comment`·추천 연쇄 삭제.
- `Comment`: 목록 조회, 작성, 수정, 삭제, 남의 댓글 조작 거부, `ADMIN`의 삭제 허용.
- 추천: `Post` 추천, 중복 추천이 쌓이지 않음, 취소, `Comment` 추천과 취소, 추천수와 "내가 추천했는지"가 응답에 정확히 반영됨.
- 설정: 애플리케이션 컨텍스트가 뜨는지 확인하는 스모크 테스트 하나.

### 프로젝트 내 선례

없다. 이 스펙이 첫 테스트를 만든다. 외부 선례로 삼을 구조는 `molip-academy/molip-academy-lms`의 back으로, 컨텍스트 로딩 테스트 하나 + 도메인별 컨트롤러 테스트 + 인증 지원 클래스 구성이다.

### front-react

자동 테스트를 두지 않는다. 컴포넌트 테스트 도구 도입은 그 자체로 별도 결정이며 이번 범위에서 정해진 바 없다. 수동으로 확인한다. **이번 스펙에서 seam이 비는 유일한 지점이다.**

> 이후 메모: 이 빈자리는 스캐폴딩이 끝난 뒤 채웠다. seam을 "사용자가 보는 화면 하나"로 두기로 했고, 근거는 [ADR-0006](../../docs/adr/0006-front의-seam은-화면-하나다.md)에 있다.

## Out of Scope

- **시리즈와 목차.** `Post` 여러 개를 순서 있게 묶는 개념. 교안을 일반 글과 구별하는 가장 큰 요소지만 다음 기능으로 미룬다.
- **코드블록 raw 공유.** 교안 안의 n번째 코드블록을 raw 텍스트로 내주는 경로. 마크다운 파싱과 코드블록 인덱싱이 선행돼야 한다.
- **대댓글.** `Comment`에 `Comment`를 달 수 없다.
- **이메일.** 필드 자체를 두지 않는다. 따라서 비밀번호 재설정도 없다.
- **소프트 삭제.** 삭제는 물리 삭제다.
- **refresh token, 토큰 블랙리스트, 서버 측 로그아웃.**
- **소셜 로그인.**
- **회원 탈퇴, 회원 정보 수정.**
- **내 정보 화면의 "내가 쓴 글 목록".** 내 정보는 `Nickname`·`Role`·가입일만 보여준다.
- **검색, 태그, 정렬 옵션.** 목록은 최신순 고정.
- **이미지 업로드.**
- **`infra`, `front-kmp`, 배포, CI.**
- **front-react 자동 테스트.**

## Further Notes

- ADR-0001에 따라 `Lesson`이나 `Material` 같은 엔티티를 만들지 않는다. 교안은 긴 `Post`다. 이걸 모르고 코드를 보면 "교안 플랫폼인데 교안이 없다"고 읽힌다.
- ADR-0002의 결과로 **로그아웃해도 그 토큰은 최대 7일간 유효하다.** 알고 넘어가는 제약이며, 해결하려면 그 ADR을 다시 열어야 한다.
- `ViewCount` 때문에 `Post` 상세 조회가 쓰기 트랜잭션이 된다. 조회마다 UPDATE가 나간다. 트래픽이 늘면 가장 먼저 문제가 될 지점이다.
- Tailwind play CDN은 스펙 초안에 있었으나 프로덕션 용도가 아니어서 제외했다. DaisyUI도 초안에 있었으나 shadcn으로 대체하기로 했다.
- Thymeleaf와 thymeleaf-layout-dialect는 초안에 있었으나, back이 화면을 그리지 않기로 하면서 사라졌다. 참고로 layout dialect는 Spring Boot 4에 맞춘 4.x가 따로 있으므로, 나중에 서버 렌더링이 필요해지면 3.x를 쓰면 안 된다.
- 결과물은 블로그다. 교안 플랫폼이 되려면 시리즈와 raw 공유가 붙어야 하며, 그게 다음 두 기능이 될 가능성이 높다.
